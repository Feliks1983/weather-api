Проект: weather-api

Обзор проекта
В этом проекте вы разработаете небольшой бэкэнд-сервис, который будет интегрироваться с внешним API погоды.

К настоящему моменту вы уже знаете, как создать сервер, определить маршруты и вернуть JSON-ответы.

Новый навык, который вы здесь практикуете, это:

Вызов стороннего API из вашего бэкэнда, преобразование ответа и возврат собственного чистого ответа API.

Ваш проект должен быть написан на Node.js + TypeScript .

Настройка
1. Инициализируйте проект.
mkdir weather-api
cd weather-api
npm init -y

2. Установите зависимости
npm install express axios dotenv cors helmet morgan
npm install -D typescript ts-node-dev @types/node @types/express @types/cors @types/morgan
Тестирование:

npm install -D jest ts-jest @types/jest supertest @types/supertest nock

Переменные среды
Создавать .env:

PORT=3000
WEATHER_API_KEY=your_api_key_here
Создавать .env.example:

PORT=3000
WEATHER_API_KEY=your_api_key_here

API для прогноза погоды: https://openweathermap.org/api

Не размещайте на GitHub реальные ключи API.

Функциональные требования

1. Конечная точка проверки состояния здоровья
Создать:

GET /api/health
Пример ответа:

{
  "status": "ok"
}

2. Текущая точка измерения погоды
Создать:

GET /api/weather/current?city=Seoul
Этот конечный пункт должен:

прочитать city параметр запроса
проверьте city предоставленную информацию.
вызвать один внешний API погоды
возвращает упрощенный JSON-ответ

Пример ответа:

{
  "city": "Seoul",
  "country": "KR",
  "temperature": 21,
  "description": "clear sky",
  "humidity": 60
}

Требования к обработке ошибок
Ваш проект должен обрабатывать следующие случаи:

Отсутствующий город
Если city не указано:

return 400 Bad Request

Пример:

{
  "message": "City query parameter is required"
}

Город не найден
Если поставщик метеорологических данных возвращает сообщение «не найдено»:

return 404 Not Found
Пример:

{
  "message": "City not found"
}

Сбой внешнего API
Если внешний API недоступен или произошла другая непредвиденная ошибка:

return 500 Internal Server Error
Пример:

{
  "message": "Failed to fetch weather data"
}

Требования к тестированию

Дымовая проверка — это быстрая базовая проверка работоспособности приложения на самом важном уровне. Она отвечает на вопрос: «Запускается ли проект, и работают ли вообще основные функции?»

Дымовая проверка

Напишите простой дымовой тест, чтобы убедиться, что ваше приложение запускается корректно и основные конечные точки работают.

При проведении дымовой проверки необходимо следующее:
Запустите приложение в тестовом режиме.
Убедитесь, что запрос GET /api/health возвращает код 200.
Убедитесь, что основной сервис прогноза погоды возвращает успешный результат для указанного города.
Убедитесь, что конечная точка погоды возвращает код 400, если город отсутствует.
Рекомендации:
используйте библиотеку для тестирования под названием Jest.
Используйте Supertest для тестирования конечных точек Express.
Проводите небольшие тесты, сосредоточив внимание на основной функциональности.
Здесь не нужно тестировать каждый частный случай; это лишь быстрая проверка работоспособности приложения.

Цель дымовой проверки — ответить на один вопрос: «Работает ли приложение и функционируют ли его наиболее важные функции?»

Что должен проверять дымовой тест?
Как минимум, проверьте следующее:

1. Конечная точка состояния здоровья

Ожидается:200 OK

GET /api/weather/current?city=Seoul
Ожидается:

city

3. Отсутствующий город
GET /api/weather/current
Ожидается:

статус400

Написание вашего первого теста SuperTest для GET-запросов
После экспорта приложения первое тестирование займет всего несколько строк кода. Импортируйте requestиз supertest, передайте ему ваш app, и объедините HTTP-глаголы и ожидания. Используйте современный стиль async/await— он гораздо более читабелен, чем старый .end()стиль с колбэками

Запустите его с помощью команды npm test.
